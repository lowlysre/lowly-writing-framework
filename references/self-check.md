# Self-check before finishing

The shared checklist for every artifact this skill governs: PR bodies, issue bodies, PR review comments, docs, code comments. Each item states which artifact(s) it applies to. A voice-pack skill layered on top may add its own checks (punctuation, phrasing taste); run those after this list, never instead of it.

Split in two, because the two kinds of check fail differently. A grep either matches or it doesn't, so run it as an actual command against the actual text; don't replace the command with "I re-read it and it looks fine," that's the judgment call these commands exist to remove. A judgment check has no regex, that's not a loophole to skip it, it means read carefully rather than trust the first draft.

## Mechanical checks (run the command, don't eyeball it)

Run each pattern with whatever the OS already provides: `grep -E` on Linux/macOS, `Select-String` on Windows PowerShell. Don't reach for `rg`, it's a fine tool but isn't preinstalled by default anywhere, so a checklist built around it needs an install step the OS-native tools don't. Applies to everything unless noted.

These commands need a file on disk. A body headed for `update_pull_request` (or any other structured tool with no shell string to write to a file) doesn't have one by default, write the drafted text to a temp file first so the checks below run as real commands, not a memory check on text that only ever existed in the tool call.

- Narrative/historical tells: `grep -inE '(removed|used to|previously|no longer|was updated|a scan found|as of #)' file` / `Select-String -Pattern '(?i)\b(removed|used to|previously|no longer|was updated|a scan found|as of #)\b' file`. Any hit in a doc or code comment means rewrite it to describe the system as it is now, or delete the line. Applies to docs and code comments, run it even when this skill wasn't the reason you opened the file.
- Hand-constructed issue-URL mistake: `grep -nE 'pull/[0-9]+#issue-' file` / `Select-String 'pull/\d+#issue-' file`. A hit is the `.../pull/456#issue-<id>` mistake in `SKILL.md` Formatting, fix it the same way that rule describes. Applies to everything.
- Missing owner/repo prefix on an issue reference: `grep -nE '(^|[^a-zA-Z0-9_./-])#[0-9]+' file` / `Select-String '(^|[^a-zA-Z0-9_./-])#\d+' file` for a bare `#123`, and `grep -nE '[a-zA-Z][a-zA-Z0-9_.-]*#[0-9]+' file` / `Select-String '\b[a-zA-Z][a-zA-Z0-9_.-]*#\d+\b' file` for a `reponame#123` missing its owner. The second pattern can't see across a `/`, so it also matches the tail end of an already-correct `owner/reponame#123`, e.g. flagging `overture-core#17` inside `OvertureMaps/overture-core#17`: check the character immediately before the match, a hit preceded by `/` is already qualified and not a real finding. Every genuine hit (a bare `#123`, or a `reponame#123` with no `/` before it) needs fixing to the full `owner/repo#123` form per `SKILL.md` Formatting, which requires it on every mention, same-repo or cross-repo. Applies to everything.
- Backticked issue reference, whole or partial: `` grep -nE '`#[0-9]+|#[0-9]+`' file `` / `` Select-String '`#\d+|#\d+`' file ``. Catches a fully wrapped `` `#123` ``/`` `owner/repo#123` `` and the sneakier partial wrap `` `owner/repo`#123 ``, where only the repo name is backticked and the closing tick sits right before `#123`. The previous check's regex doesn't see a backtick, so it won't flag either shape; any hit here still needs fixing per `SKILL.md` Formatting. Applies to everything.
- Non-closing issue phrasing: `grep -inE '(part of|relate[sd]? to).*#[0-9]+' file` / `Select-String -Pattern '(?i)\b(part of|relate[sd]? to)\b.*#\d+' file`. Per `references/pr-writing.md` there's no justified exception, any hit gets rewritten: if the PR is a slice of the referenced issue, scope a sub-issue to what this PR delivers and close that instead. Pair with confirming a closing keyword exists at all: `grep -inE '(fixes|closes|resolves)' file` / `Select-String -Pattern '(?i)\b(fixes|closes|resolves)\b' file`, zero hits means the PR needs an issue to close, made from scratch if none fits. Applies to PR bodies.
- Bare URLs: `grep -nP '(?<!\]\()https?://' file` / `Select-String '(?<!\]\()https?://' file` (the negative lookbehind needs `-P` in grep; plain `-E` won't do it). Every hit still needs a manual look: the lookbehind skips a URL already wrapped in `[text](url)`, but a reference-style link (`[text][ref]` with the URL defined elsewhere) or a URL sitting inside a code span still slips through. A real hit needs a named link, per `SKILL.md` Formatting; ignore bare GitHub issue/PR URLs, that rule's exception. Applies to everything.
- Backtick pileup: `` grep -nE '(`[^`]+`,[[:space:]]*){3,}`[^`]+`' file `` / `` Select-String '(`[^`]+`,\s*){3,}`[^`]+`' file ``. A hit is the four-or-more-in-a-row case `SKILL.md` Formatting flags, restructure the same way that rule describes. Applies to everything.
- Decorated review-comment labels: `` grep -nE '^[[:space:]]*(\*\*|`)(praise|nitpick|suggestion|issue|question|thought|chore|note)' file `` / `` Select-String '^\s*(\*\*|`)(praise|nitpick|suggestion|issue|question|thought|chore|note)' file ``. A hit means a label got bolded or backticked; `references/review-comments.md` keeps them plain text. Separately confirm the comment opens with one of those labels at all. Applies to PR review comments.
- Missing AI watermark: `grep -c '<!--:robot:-->$' file` / `Select-String '<!--:robot:-->$' file`. Zero hits, or a hit that isn't the literal last line, means the `## AI watermark` rule in `references/pr-writing.md` didn't take; add it as its own last line. Applies to PR bodies and PR/review comments only, not docs, code comments, or issues.
- Hard-wrapped paragraphs: `grep -vE '^([[:space:]]*([#>*-]|[0-9]+\.|\||\`\`\`)|[[:space:]]*$)' file | awk '{ if (length($0) < 90) print NR": "$0 }'` / `Get-Content file | Where-Object { $_ -notmatch '^\s*([#>*-]|\d+\.|\||```)' -and $_.Trim() -ne '' -and $_.Length -lt 90 }`. Skips headings, list/quote/table lines, and fences, then flags any remaining prose line short enough to be a manual wrap instead of a full paragraph. A hit means rejoin that paragraph into one line per `SKILL.md` Formatting; a genuinely short one-line paragraph is a false positive, confirm by eye before rejoining. Applies to PR bodies, issue bodies, and docs.
- Verify what actually landed, per `references/gh-cli.md`'s Verifying what landed section: after any `gh api`, `gh pr comment`, `gh issue comment`, or `gh discussion comment` post/edit, re-fetch the live body and diff it against the draft (a `-f body=@path` typo posts the literal string `@path` and still exits 0), and once a PR is pushed, confirm a closing-issue reference actually linked rather than trusting the rendered keyword text. Applies to PR bodies, PR/review comments, issue comments, and discussion comments.
- Body length: `(Get-Content -Raw file).Length` on Windows, `wc -c < file` elsewhere, after deleting any fenced ` ```mermaid ` blocks first, those render as an image and don't count toward the ceiling, per `references/body-writing.md`. Past roughly 3,000 characters of what's left, headings alone don't satisfy that file's length ceiling, that's organizing a wall of text, not shrinking it. Cut prose or collapse on-demand detail into `<details>`; don't use this as a reason to split the PR or narrow the issue, per `SKILL.md`'s Boundaries rule the scope isn't the writing's to negotiate. Applies to PR bodies and issue bodies.
- Over-quoted anticipated-reviewer-question: `` grep -Pzo '(?ms)^>.*\?[ \t]*\n>[ \t]*\n>' file `` / `` (Get-Content -Raw file) -match '(?ms)^>.*\?[ \t]*\r?\n>[ \t]*\r?\n>' ``. Matches a `>`-quoted line ending in a question mark, a blank quoted line, then another quoted line, the answer got blockquoted along with the question. Per `references/body-writing.md`'s Anticipated reviewer questions section, only the question keeps the `>`, the answer is plain unquoted text starting on its own line with no `>`. This doesn't false-positive on a multi-line `> [!NOTE]`-style admonition, those don't open with a line ending in `?`. Applies to PR bodies and issue bodies.

## Judgment checks (no regex substitutes for reading it)

- Re-check every testing/verification claim in the PR body against the diff as it stands now, not as it stood when the claim was first written. A claim can go stale silently across later edits to the same PR (a diagram switched from drawio to mermaid, a manual step replaced) without anyone touching the sentence describing it. That's drift, not fabrication, but it still misleads the reviewer, so treat an unverified claim the same as a false one. Applies to PR bodies.
- Count the paragraphs before the body's last section (`## Testing` for a PR, or the last template section for an issue) in the finished text: the "3 paragraphs max" rule in `references/body-writing.md` is easy to satisfy while drafting and still miss once the body's assembled, an admonition or a version-bump one-liner can pad the count without you noticing it crossed the threshold. 4 or more substantive paragraphs needs `###`/`####` headings, or a diagram/citation/`<details>` to cut the count back down, per that file's Body structure section; go back and fix it rather than shipping as-is. Applies to PR bodies and issue bodies.
- Scan for asides left sitting in the main narrative: a sentence starting "also fixed", "while I was in there", "noticed", or describing a change unrelated to the paragraph around it, is a tangential fix that hasn't been pulled into its own `Bonus`/`Chores`/`Also fixed` sub-header per `references/body-writing.md`. Move it out rather than leaving it inline just because it's short, brevity doesn't substitute for the section break the reader needs to know it's skippable. Applies to PR bodies and issue bodies.
- Read every top-level bullet in a flat list (`Bonus`, `Also in this PR`, or similar) on its own: one running 3+ sentences deep, or stacking a mechanism, a rationale, and a filed-issue reference behind semicolons and commas, is the flat-list-with-multi-line-items case `SKILL.md` Formatting bans, not a bullet. Split it into nested sub-bullets, one clause per line, per that rule; a bullet that needs its own trailing "It exists for..."/"Filed as..." sentence is the tell. This is also where backtick density actually piles up, four or five inline-code spans strung through one dense bullet reads the same as the comma-separated case the mechanical check catches, splitting the bullet fixes both at once. Applies to PR bodies and issue bodies.
- Gauge the body's altitude against the diff's size: a large PR described symbol-by-symbol reads as prose strung with backticked function and variable names, even when no single sentence trips the mechanical backtick-pileup check. Per `references/body-writing.md`, big changes get described at the module/package/class level, with the diff carrying the function-level detail; rewrite the offending passages a layer up rather than pruning backticks one at a time. Applies to PR bodies.
- Check for banned AI-era phrases: scan the draft against `references/banned-phrases.md`. Any hit needs either a concrete replacement (say the number, the mechanism, the specific thing) or deletion. A word that appears in a technical identifier or a quoted error string is not a hit. Applies to everything.
- Check the ratio. A comment longer than the code it explains, or a PR/issue body longer than the diff or ask it describes, means the prose is carrying weight the code should carry. Usually the culprit is a paragraph defending a decision, which is complexity smuggled back in as prose. Either make the code clear enough to need less explaining or cut the explanation. The `Never trim these` list in `SKILL.md` is exempt. Applies to code comments, PR bodies, and issue bodies.
- Count the lines in every comment block. Per `references/docs-and-comments.md`, 5 lines is the hard cap and most comments should fit in 1-2; a block still running past 5 lines is an explanation the code should carry, not a comment. Split the logic into a well-named helper, shorten the comment, or move the detail into a docstring/README. Applies to code comments.
- Confirm any "not covered here" or scope-boundary note is actually load-bearing, not restating structure a linked sub-issue or tracking issue already shows. Per `references/body-writing.md`, keep it only when it surfaces something the reader wouldn't otherwise see. Applies to PR bodies and issue bodies.
- For every issue/PR number cited in a code comment, confirm it's a posterity `TODO`, a future reader after this project's current context is gone, not a fast-follow or already-slotted next-up item, per `references/docs-and-comments.md`. If the linked work is expected to land soon or is already planned, the comment is a cleanup chore waiting to happen, describe current behavior instead. Applies to code comments.
- Confirm over-arching context (a parent/tracking effort, a prior decision, a constraint set elsewhere) sits in a `## Context` section at the very top, not folded into a later paragraph or left implicit. Per `references/body-writing.md`'s Context section, this only applies when there's wider context to state, don't add the section to a standalone issue or PR with no parent effort. Applies to PR bodies and issue bodies.
- Check the `## Testing` section against the repo's CI config, not just against the diff: a sentence like "ran the test suite" or "ran the linter locally" is redundant proof, not honesty, when the same command already runs on every push. Per `references/pr-writing.md`, cut any line CI re-runs on this PR anyway, keeping only what CI doesn't cover. Applies to PR bodies.
- For every "testing wasn't possible" or "couldn't test X" line, name the concrete test, script, or documented manual step it refers to. If none exists, that's not a gap, it's an invented bar the project never held itself to ("couldn't fully end-to-end test this" with no e2e suite in the repo), per `references/pr-writing.md`; delete the line rather than leave manufactured doubt in the body. Applies to PR bodies.
